# Account access management

Implemented locally on `feat/identity-access-management`; not deployed. Open `/app/access/` as a current verified Google administrator. All screens use current API records and English, Simplified Chinese and Spanish labels.

## Owner workflow

**Accounts** lists verified Google sign-ins, with name/email, role and status filters and backend cursor pagination. Choose Edit access, select administrator/employee roles and employee houses, enter a reason, and save. Customer access belongs to every verified Google identity and covers only its own permitted records; it cannot be removed independently or used to link another customer's records. Existing administrator-approved customer linking remains separate.

Suspend access blocks all workspace API access immediately and preserves the Google login, roles, house assignments and business records. Restore access reverses that application suspension. A Firebase-disabled account is displayed separately; these controls cannot enable a disabled Google/Firebase login, edit credentials, or delete accounts. The acting administrator cannot remove their own administrator access or suspend themselves. Concurrent changes retain an active administrator.

**Invitations** supports new Google accounts that have not signed in yet. Create an invitation with reviewed roles/houses, then copy the one-time code and share it privately. No email is sent. The code is shown only in the successful form session and expires after 24 hours. Ask the recipient to sign in with the invited Google email, open My profile and choose Accept invitation. The generic acceptance entry is `/app/account/profile/?dialog.access-accept=true`; share the code separately, never in a URL. If a code is lost, cancel the pending invitation and create another. Existing signed-in accounts are managed under Accounts.

Acceptance requires the exact verified email, an active unexpired invitation and an issuing administrator who still has access. It grants reviewed staff roles/house assignments atomically, without linking, merging or moving customer records. An account that already has staff access must be reviewed directly. Cancelled, expired or used codes cannot be accepted again. **Change history** shows persisted before/after values, responsible identities, timestamps and reasons.

If a save's response is lost, inputs remain frozen. Retry sends the identical operation. If another edit changed a reviewed version, close the form, refresh and reopen to review the latest state.

## Enforcement and storage

- `firebaseIdentity(auth, db)` verifies revoked tokens, current Firebase account status, verified email and Google provider. `accountAccess/{sha256(uid)}` supplies current staff flags and active/suspended state when present; unmanaged identities retain exact-boolean legacy Auth bootstrap claims. A managed policy is authoritative even if an old token or Firebase custom claim still says administrator. The portal routes using `/api/identity`, refreshes on visibility and access-change events, and rechecks visible sessions every minute. Every API request checks current policy independently of browser refresh.
- Role management does not call `setCustomUserClaims`, update Google credentials or disable Firebase accounts. Firebase documents that [custom-claim token propagation occurs on token refresh or a subsequent sign-in](https://firebase.google.com/docs/auth/admin/custom-claims); current Firestore policy checks avoid relying on that delay. Existing `firebaseauth.users.get` and database access remain sufficient; no Auth write role, secret, email provider or additional service is introduced. A final hosted release must verify runtime directory permission before activation.
- Access changes transactionally check the current actor policy, target policy version and `employeeAssignments/{uid}` version, configured houses, shared `accessControl/serialization` lock and stable `accessOperations/{operationId}` receipt. They save policy, assignments, assignment history, immutable `accessHistory` and receipt together. Competing administrators cannot demote each other or resurrect stale assignments. The legacy employee-assignment API now honors managed roles and rejects races on its assignment version.
- Last-admin protection includes current managed policy candidates and legacy Auth bootstrap administrators. External Firebase/Firestore project administrators remain trusted operators; app transactions cannot serialize their out-of-band account deletions, disablement or direct database changes.
- `accessInvitations/{id}` contains normalized email, reviewed roles/houses, status/version, creation/expiry times, issuer and SHA-256 code digest. The browser creates 192 random secret bits and keeps the code in form memory for identical retries. `accessInvitationEmails/{sha256(email)}` serializes competing invitations. No read DTO, receipt, history entry, URL, browser storage or screenshot contains a usable invitation code. Acceptance is rate-limited, checks issuer authority and writes policy/assignment/claim/audit/receipt in one Firestore transaction.
- Directory reads scan Firebase Auth pages on the server, batch-load policy/assignment projections, filter before page sizing, and return permitted fields only. Cursor bindings include filters and page size. Sparse searches scan to a match/exhaustion rather than reporting a false empty first page. No entire directory is downloaded into the browser. This prioritizes current Auth state; very large directories may warrant an indexed identity catalog later.
- History and invitations use descending `at`/document-ID cursor order; default single-field indexes cover those reads. Direct browser Firestore access remains denied. No retention/deletion policy is invented.

## Release and recovery

Deploy the policy-aware API before the frontend in the final combined Google Cloud release. Once Access has managed an account, retain a policy-aware backend for rollbacks: pre-Access APIs would trust the old bootstrap claims. Do not roll back to those revisions. All runtime entry points and test servers must pass Firestore to `firebaseIdentity`; there is no policy-bypassing optional database mode.

`npm run admin:access` remains an unmanaged-account bootstrap tool. It reads the policy first and refuses to change claims for a managed account, rather than falsely reporting a grant/revocation that the authoritative policy would override. Routine changes use Access. A project-admin break-glass recovery, if ever required, must preserve policy/assignment versions and audit evidence; do not delete a policy to revive old claims. This task does not modify production IAM, Firebase identities or production records.
